Why Outlook breaks things

Outlook for Windows doesn't render HTML with a browser engine — it hands the message to Word's HTML renderer. Word supports a subset of CSS from roughly 2000, ignores the rest silently, and applies its own paste-mode rules on top. Every pattern below exists because something that looks correct in Chrome renders wrong, or not at all, once it passes through that pipeline.

01

Two renderers, one document

The editor and the export function never share output — they read the same Tiptap document but disagree on purpose. Design tools this way whenever the editing surface (browser-rendered) and the delivery surface (a foreign rendering engine, a printed page, a different app) have different capabilities.

Editing surface

Vue NodeViews render live in the browser. Full CSS available: flex, custom NodeView chrome, hover states, drag handles. Optimized for manipulation, not fidelity.

Export surface

emailExportHtml.ts walks the same document a second time and rebuilds it as nested tables with inline styles and legacy tags — optimized for surviving Word's renderer, never shown on screen.

02

Merge inline styles, never overwrite

mergeStyle()

Root cause of the fidelity round

The original export code replaced an element's style attribute wholesale with computed defaults, silently discarding anything already set — that's why callout/banner fills, text color, and highlight color kept vanishing on paste even though the editor showed them correctly.

function mergeStyle(existing: string, defaults: Record<string, string>) {
  // existing declarations win — defaults only fill gaps
  const parsed = { ...defaults, ...parseStyle(existing) }
  return Object.entries(parsed)
    .map(([k, v]) => `${k}:${v}`)
    .join(';')
}

Applied everywhere the export pipeline touches an element that might already carry author styling: table cells, headers, blockquotes, banners.

03

Legacy <font> tags for character runs

wrapCharacterRunsInFont() + stampMsoHighlight()

Word quirk

Text color, size, and highlight are set with modern CSS in the editor (color, background-color, font-size). Word's "Merge Formatting" paste mode — a client-side setting outside the app's control — drops modern character-run CSS but honors the ancient <font color> tag and Word's own mso-highlight property.

Color
wrap the run in <font color="#…"> in addition to the CSS
Highlight
stamp both background: and mso-highlight: on the span
Size
pxToFontSize() maps px to Word's 1–7 <font size> scale
note

"Merge Formatting" itself can't be fixed from the app side — it's a per-recipient Outlook preference. These tags are a hedge that makes the common case (Keep Source Formatting, or Merge Formatting with the fallback tags present) survive; there's no HTML that defeats a user's own paste-mode choice.

04

The bulletproof-button table

tableizeButtons()

Bug: button rendered oversized

A styled <a> with padding renders correctly in every browser but stretches to fill its container in Word — the classic email-dev complaint. The standard fix is a single-cell table where the cell is forced to its minimum content width.

<table role="presentation" cellpadding="0" cellspacing="0">
  <tr>
    <td width="1" style="white-space:nowrap; mso-padding-alt:12px 24px;"
        bgcolor="#2f5aa0">
      <a href="..." style="color:#fff; text-decoration:none; display:block;">
        Click Here
      </a>
    </td>
  </tr>
</table>

width="1" looks wrong but is the trick — it forces Word's table layout down to the cell's minimum, and white-space:nowrap stops the label wrapping once the cell is that narrow, so it re-expands to fit the text exactly.

05

Crop pixels, don't fake it with CSS

cropImageToAspect()

Corrected mid-session

First attempt: object-fit: cover plus fixed width/height attributes. Looked right in the browser, distorted in real Outlook — Word has no concept of object-fit, so it forces the raw image into the stated box. The client correction was explicit: keep the full-width, no-padding banner behavior, but make the pixels themselves already the right shape.

async function cropImageToAspect(src: string, aspect: { w: number; h: number }, outputWidth = 1280) {
  const img = await loadImage(src)
  const canvas = document.createElement('canvas')
  canvas.width = outputWidth
  canvas.height = Math.round(outputWidth * (aspect.h / aspect.w))
  const ctx = canvas.getContext('2d')!
  // cover-style crop: scale to fill, center-crop the overflow axis
  drawCover(ctx, img, canvas.width, canvas.height)
  return canvas.toDataURL('image/png')  // stored — not recomputed on every render
}

Because the stored src is already exactly 640×140 or 640×100, no CSS trick is needed on either the editor surface or the export surface — the two renderers finally agree, because there's nothing left for either of them to interpret.

06

Trailing-node safety, with one exception

EmailTrailingNode

Client correction: don't disable it globally

StarterKit's built-in TrailingNode re-appends an empty paragraph whenever the document ends on a non-text atom — normally good UX (always somewhere to keep typing) but it re-created the exact empty-space-below-the-footer bug on every transaction. Disabling it outright broke that same safety net for tables, callouts, and header/plain images. The fix is the one-line exception, not the blanket flag.

appendTransaction: (transactions, _oldState, state) => {
  if (!transactions.some(tr => tr.docChanged)) return null
  const last = state.doc.lastChild
  if (!last) return null
  if (last.type.name === 'paragraph') return null
  if (last.type.name === 'image' && last.attrs.role === 'footer') return null
  return state.tr.insert(state.doc.content.size, state.schema.nodes.paragraph.create())
}
07

Insert first, strip second

moveToEdge()

Caused an actual tab hang

Auto-positioning a header/footer image to the true top/bottom of the document, then cleaning up the empty paragraph it leaves behind, seems like strip-then-insert. Doing it in that order can walk the document to zero block children mid-transaction — ProseMirror's schema minimum silently refills a new empty paragraph the instant that happens, and a naive cleanup loop sees that fresh paragraph as "still empty" and deletes it again. Forever. A real infinite loop, not just a logic gap.

Strip, then insert

Doc can hit 0 children mid-transaction → schema auto-refills a paragraph → cleanup loop never terminates.

Insert, then strip

The image itself always satisfies the schema minimum, so childCount never hits zero — every other empty sibling can be removed safely.

08

Scope stopEvent to the chrome, not the node

EmailImage NodeView options

Made the image unselectable

An unconditional stopEvent: () => true was meant to stop the settings-gear popover from triggering ProseMirror's own selection logic — but it swallowed every event on the node, including a plain click on the image itself, so the image could never be selected (and the alignment toolbar could never apply to it).

addNodeView() {
  return VueNodeViewRenderer(EmailImageNodeView, {
    stopEvent: ({ event }) =>
      !!(event.target as HTMLElement | null)?.closest('[data-email-image-chrome]')
  })
}

Only events that originate inside the gear popover's marked chrome are swallowed — a click anywhere else on the node falls through to ProseMirror's default click-to-NodeSelection behavior, same as any other atom.

09

Fake the href on screen, make it real on export

ButtonLink.href ↔ data-href

Final fix, after two failed attempts

A real <a href> in the editor competes with ProseMirror for the click — intercepting the click event (preventDefault, then a manual mousedown handler resolving position via posAtDOM) worked in one test and silently navigated the tab in the next. Removing the real href entirely removes the competition instead of refereeing it — a bare <a> with no href is not navigable by any browser.

// tiptapExtensions.ts — the node's own attribute definition
href: {
  default: '',
  parseHTML: el => el.getAttribute('data-href') || '',
  renderHTML: attrs => ({ 'data-href': attrs.href || '' })
}

// emailExportHtml.ts — the export step is the only place a real href appears
const href = el.getAttribute('data-href') || '#'
gotcha

A node's renderHTML({ HTMLAttributes }) parameter is the already-merged output of every attribute's own renderHTML — not the raw node attrs. An attribute whose own renderHTML intentionally returns {} (like align here, which only affects a wrapping element) will read back as undefined from HTMLAttributes. Read node.attrs.align directly instead.

Porting checklist

Before reusing any of this on a new template surface — a different email builder, a PDF export, a print stylesheet — walk this list.

  • 01Does the target renderer disagree with the browser? If export and edit surfaces are the same engine, most of this doesn't apply — go straight to a shared render path instead of two.
  • 02Merge styles, never overwrite them, anywhere the export pipeline touches an element a user may have already styled.
  • 03Never crop or resize with CSS if the target renderer might not honor the CSS property doing the work — crop the actual pixels once, at insert time.
  • 04Order transaction operations around schema minimums. Insert the node that will satisfy the minimum before stripping anything, never after.
  • 05Scope stopEvent to the smallest DOM region that needs it, not the whole node — the default click-to-select behavior is usually worth keeping.
  • 06If a live element competes with the framework for a click, remove the competing native behavior at the source rather than intercepting the event.
