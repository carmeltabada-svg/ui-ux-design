# Data Contract: AMS Retrieval Module

**Status:** Draft, written before the developer has reviewed the prototype. Every table,
column and endpoint below is a **proposal** taken from what the front end currently holds.
Where a decision is needed, this document states a **default assumption** (section 10) so
the front end can be built now. The developer owns the final schema, migrations and
conventions and can change any default after the demo. Nothing here has been built on the
backend.

**Stack assumed:** Laravel + MySQL (managed through Workbench and phpMyAdmin). The front
end is Nuxt/Vue and talks to the backend over JSON.

**Source of truth for shapes:** `app/data/ticketTrackers.ts` (tickets and related),
`app/data/retrievalForms.ts`, `app/data/templateRuntime.ts`, `app/data/templates.ts`,
`app/data/checklistTemplates.ts`. These files are a reference for which fields exist. They
must not survive as the store (see `DEV_HANDOFF.md` §10.2).

## 2. Conventions

### 2.1 Database (Laravel defaults)
- Tables are plural snake_case. Primary key is `id` (`bigint unsigned`, auto-increment).
- Foreign keys are `<singular>_id` (`ticket_id`) with a real foreign key constraint.
- Every table has `created_at` and `updated_at`. Add `deleted_at` (soft delete) where noted.
- Status and type columns are `string` and backed by PHP enums. Do not use MySQL `ENUM`
  (hard to change later). Allowed values are in section 5.
- Money is `decimal(12,2)`. Never float.
- **Date-only values** (`lwd`, `target_date`, `separation_date`) are `date`.
  **Moments in time** (`sent_at`, `confirmed_at`) are `timestamp` stored in UTC.
- Free text that the UI shows as a list item is a row, not a JSON blob (see 4.3 for the
  checklist, which the prototype stores as parallel arrays).
- Use `json` only for genuinely schemaless payloads (history `details`, form field
  definitions).

### 2.2 Identity and time belong to the server
The front end never generates these. The prototype fakes them in the mock layer only.

| Value | Generated by |
|---|---|
| `id`, `ticket_number` | Database (`ticket_number` is a separate unique column, see 4.1) |
| `reference` (`APR-YY-NNNNN`), `atd_reference`, `audit_trail_id`, gate pass `ref` | Server, at the moment the record is created or the stage is reached |
| `acknowledgment_token` | Server (random, unguessable, unique) |
| `created_at`, `updated_at`, every `*_at` action timestamp | Server clock (UTC) |
| Actor on every action (who did it) | The authenticated user, never a value sent by the client |

### 2.3 JSON naming
Laravel API Resources return **snake_case**. The prototype uses camelCase everywhere.
Default plan: the front end converts at one boundary (`app/api/`), so no page changes. If
the developer prefers camelCase from the Resources, only that boundary changes.

### 2.4 Lookup by ticket number
URLs use the user facing ticket number (`/ticket-tracker/426`), not the internal `id`.
Use `getRouteKeyName()` returning `ticket_number`, or a dedicated lookup endpoint.

## 3. Who owns what

### 3.1 Team member data: AMS first, R24 only for what the AMS lacks
**Updated by decision.** The AMS already holds team member records: personal email,
contact number, alternate contact, address, client, position and assigned assets. Read those
from the AMS; do **not** fetch them from R24. From R24 fetch only what the AMS does not
have, per ticket and read only: last working day, separation date, shift, department, leadership coach, mode and the
suggested reason from the offboarding case (INTEGRATIONS.md section 3). Do **not** store R24 data in AMS tables.

The prototype embeds a whole `HrisRecord` inside every ticket, mixing both sources. Replace
it: the ticket stores the AMS team member id, the AMS asset id per unit, the per ticket
contact verification flags and address correction (4.1), and one value, `lwd_seen`, the last
working day the current Target Date was computed from, so a later change in R24 can be
detected. Everything else from R24 is fetched when needed. The full field list, the
consequences and the questions to confirm are in INTEGRATIONS.md section 3.

### 3.2 In the AMS database (this document)
Tickets and everything hanging off them, courier providers and branches, checklist
templates, email templates, retrieval forms and their versions, notifications.

### 3.3 Stays in front end code (do NOT create tables for these)
These are constants in the prototype, not data an operator edits. Keep them in code unless
the product decides to make them editable.

| In code | File |
|---|---|
| Stage engine: `STAGE_META`, `MATRIX` (path matrix by reason and mode), `GATE_STEPS` | `ticketTrackers.ts` |
| Display labels, colours, icons for every enum (`REASON_LABELS`, `ASSET_CATALOG`, ...) | various |
| SMS copy (`SMS-1A` to `SMS-11`) and the call escalation SMS | `smsTemplates.ts`, `templates.ts` |
| Token definitions for email placeholders (`TOKEN_GROUPS`, `SAMPLE_VALUES`) | `templates.ts` |
| Page sizes and margin presets for forms | `retrievalForms.ts` |

Decision for the developer: the stage rules (which stage is next, how the target date is
computed, gate requirements) currently run in the browser. Recommended: the server
enforces them and the front end only displays the result (default assumption, section 10, item 1).

### 3.4 Prototype only (deleted at handoff, never a requirement)
Simulator bar (state, persona, scenario, situation), the demo notification functions, demo user switch
(`ams:demo:currentUser`), `simulateHrisLwdUpdate()`, the mock's own
storage (`ams:tickets:v1`, `ams:mock:emailTemplates`, `ams:mock:retrievalForms`,
`ams:checklistTemplates:v2`, `ams:formSubmissions:v1`, `ams:formPreviewValues:*`,
`ams:digest:lastDay:*`).

### 4.3 `ticket_history` (structured, not free text)

The prototype stores `{ action: string, actor, when, category }` and then **parses `action`
back with regular expressions** to rebuild the display (`ticket-tracker/[id].vue`, the
`^Retrieval cancelled: (.+?) \((.+)\)...` rule). That does not survive a database: editing a
message would break the screen, and the text cannot be filtered or reported on.

| Column | Type | Notes |
|---|---|---|
| `ticket_id` | fk | R |
| `category` | string | R. enum `HistoryCategory` (section 5) |
| `action_code` | string | R. Stable machine code, e.g. `ticket.cancelled`, `asset.confirmed`, `notice.sent` |
| `details` | json | The parameters the message needs, e.g. `{ "reason": "recall-reversed", "note": "..." }` |
| `actor_id` | fk users, null | null for system events |
| `occurred_at` | timestamp | R |

The front end builds the sentence from `action_code` + `details`. Do NOT store
`navigation` events (Back/Forward between stages). They are UI noise and are not business
events.

### 4.4 Master data

| Table | Columns | Source |
|---|---|---|
| `courier_providers` | `slug` (unique, `jrs-express`), `name`, `priority` (`recommended`, `alternate`), `account_manager`, `account_manager_email`, `corporate_account` (bool), `account_number`, `status` (`active`, `inactive`), `tracking_website_url` | `CourierProvider` |
| `courier_branches` | `courier_provider_id`, `name`, `address`, `city` | `CourierBranch`. The prototype's own note says production needs a courier API or an upload for this list |
| `checklist_templates` | `name`, `created_at`, `updated_at` | `ChecklistTemplate` |
| `checklist_template_tasks` | `checklist_template_id`, `position`, `text`, `required` (bool) | `ChecklistTemplate.tasks[]` |
| `checklist_template_defaults` | `checklist_template_id`, `reason` (null = any), `mode` (null = any). A path belongs to one template: unique on (`reason`, `mode`) | `defaultFor` (`'resignation:remote'`, `'*'`) |

A new ticket is issued a **copy** of the matching template's tasks into
`ticket_checklist_items`. The ticket's list is its own afterwards and nothing links back.

**Resource shape the front end expects** for a checklist template (see
`app/mocks/checklist_templates.json`):
```json
{ "id": "tpl-standard-offboarding", "name": "Standard offboarding",
  "tasks": [ { "text": "...", "required": true } ],
  "default_for": [ "*", "resignation:remote" ],
  "created_at": "2026-09-01", "updated_at": "2026-09-01" }
```
`tasks` is ordered. `default_for` is the template's rows in `checklist_template_defaults`
written as `reason:mode` keys, with `*` for "every other path".

**Rules the server owns** (the prototype's mock applies them so the screens behave
realistically): names are unique, case insensitively. A path belongs to one template, so
saving a template that claims a path removes it from the template that had it. The last
template cannot be deleted, and deleting one moves its paths to the first remaining
template. A rejected write returns HTTP 422 with Laravel's standard body. The front end
shows the first message under `errors`, else `message`, as is.

**Resource shapes the front end expects** (see `app/mocks/email_templates.json` and
`app/mocks/retrieval_forms.json`):
- An email template is returned with its `key` (`t1`, `t16`), `name`, `mode`, `when`
  (the description), `attachment` (label), `attachment_form_id` (a form `id`), `subject`
  and `body`.
- A retrieval form is returned with its `id` (the slug, e.g. `return-ack-onsite`), `name`,
  `description`, `mode`, `status`, `updated_at`, `theme_color`, `page_size`, `category`,
  `name_manually_set`, and `content` (the document HTML) in the same object, so the editor
  needs one request. The slug is exposed as `id` because ticket logic and email templates
  refer to forms by it.

`content` is stored as the editor document (HTML) and must be sanitised on the server
before saving (`DEV_HANDOFF.md` §8.9). The front end also escapes on render, but a second
layer is required.

Seeded template keys (`t1`, `t16`...) and form slugs (`return-ack-onsite`) are referenced
by ticket logic (`COURIER_ENDORSEMENT_TEMPLATE_KEY = 't18'`, `MATRIX[...]`). Keep them as
stable `key` / `slug` columns and do not renumber.

### 4.6 Notifications
Use Laravel's built in database notifications (`notifications` table: `id` uuid, `type`,
`notifiable_id`, `data` json, `read_at`) instead of a custom table.

Map from `AppNotification`: `data` carries `ticket_number`, `title`, `description`, `kind`
(`NotificationKind`), `action` (bool), `dedupe_key`, `delivery` (`now` or `digest`).
`dedupe_key` must be unique per notifiable so an alert is never raised twice. The morning
digest and the emailed copy are server jobs. The prototype only simulates them.

### 4.7 Users
`assignee`, `actor`, `by` are all users. Use Laravel's `users` table. The demo
`AssetTeamMember { name, email }` list and the demo persona switch are replaced by the
authenticated user and a role (Asset Team member). Roles and permissions are in
`DEV_HANDOFF.md` §10.3.

## 6. Derived values: do NOT store

The front end (or the API Resource) computes these. Storing them creates two sources of
truth that drift.

| Value | Computed from |
|---|---|
| Ticket status label and tone (`Hold Off`, `Overdue Return`, `Pending Return`...) | `ticketStatusLabel()`: stage, inspection route, dates |
| Overdue Return | `isOverdueReturn()`: target date vs today. Never a manually set flag. (`overdue_forced` is the one operator override and is stored) |
| Transit delayed | `isTransitDelayed()`: `transit_confirmed_at` + 14 calendar days |
| Days left, "Due today", "Overdue by Nd" | dates vs today |
| Acknowledgment due date, target date suggestions | path matrix rules |
| Forms attached badges in the ticket list | which forms have been sent |
| Shipment status | `shipmentStatus()` |
| First name of the team member | first word of `employee_name` unless overridden |
| Page counts, progress counts (checklist done) | rows |

If the server ever needs a derived value for sorting or filtering (e.g. "overdue" list),
compute it in a query or accessor, not a stored column.

## 7. Endpoints (proposal)

JSON over HTTPS. Auth: Laravel Sanctum (SPA cookie auth, so the first write needs
`GET /sanctum/csrf-cookie`). All routes require authentication except the public
acknowledgment link.

### 7.1 Tickets
| Method and path | Purpose |
|---|---|
| `GET /api/tickets` | List. Query: `scope=all\|mine`, `status`, `mode`, `search`, `page`, `per_page`, `sort`. The prototype loads every ticket at startup, so paging is the developer's to add |
| `POST /api/tickets` | Create. Body: `employee_id`, `reason`, `mode`, `authorizing_endorsement`, `authorizing_endorsement_date`, `recall_effective_date?`, `assignee_email?` (the prototype's Asset Team members have no id, so the email identifies one; the default is the signed in user), `reason_override_note?`, `mode_override_note?` (why the operator changed the suggested reason or the derived mode). The server takes the team member's dates, contact details and assets from HRIS, issues the checklist from the matching template, writes the first history lines and returns the full ticket (`{ "data": { ... } }`, the same shape as in the list). 422 if the person already has an open ticket. The front end shows the error message as is |
| `GET /api/tickets/{ticket_number}` | Full ticket with children (assets, checklist, gates, history) |

Everything else an operator does to an open ticket is an **action** (7.2).

### 7.2 Ticket actions
Every change to an existing ticket is `POST /api/tickets/{ticket_number}/actions/{action}`.
The body holds the arguments below. The server checks the rules, applies the change, writes
the history line (as the signed in user, in the same transaction), and answers with
`{ "data": { "ticket": { ... }, "result": ... } }`: the whole updated ticket in the same shape
as 7.1, and whatever the action itself answers. The front end never writes history or
notifications. A refused action is a 422 with `message` (and `errors` when it is about a field).

The same list, with the same names and arguments, is `ACTIONS` at the bottom of
`app/api/ticketActions.ts`, and the functions above it are the rules, written out in code.
The developer may prefer one route per action (`/assets/confirm`, `/it-lock/schedule`):
only `app/api/http.ts` changes.

### 7.4 Sending an email
`POST /api/tickets/{ticket_number}/emails`. Body:

| Field | Type | Notes |
|---|---|---|
| `stage` | string | The step that sent it (`A6`, `B9`, ...) |
| `kind` | string | `notice`, `courier-endorsement`, `branch-request`, `reminder`, `overdue`, `charging` |
| `template_key` | string | An active email template |
| `form_id` | string, nullable | The form to attach |
| `to`, `cc`, `bcc` | string[] | The page sends the team member (or the courier account manager at B9) and the template's CC and BCC |
| `idempotency_key` | uuid | One per attempt. A retry of the same attempt reuses it. A repeat returns the first result |
| `outcome` | string, optional | Only for `charging` |

The server loads the ticket, template and form, **renders them from the ticket's own data** (rules in
TEMPLATES_SPEC section 6; the reference implementation is `app/utils/ticketMessage.ts`), and answers
**422** with a message when a placeholder cannot be filled or a recipient is missing. It sends, stores a
snapshot (the `emails` table below), applies the stage's bookkeeping (the history entry and flags, as the
recorder actions do) in one transaction, and answers `{ "data": { "ticket": { ... }, "email": { ... } } }`.
A failed delivery answers an error, changes nothing on the ticket, and should store a failed `emails` row.

`emails` (one row per attempt): `id`, `ticket_id`, `kind`, `stage`, `template_key`, `form_id`, `to`, `cc`, `bcc`
(json), `subject`, `html`, `form_html` (the rendered message and attachment as sent), `status`
(`queued`, `sent`, `failed`), `error`, `sent_by_id`, `sent_at` (UTC timestamp), `provider_message_id`,
`idempotency_key` (unique per ticket).

### 7.3 History and notifications
| Method and path | Purpose |
|---|---|
| `GET /api/tickets/{ticket_number}/history` | Paged, filter by `category`. (The prototype reads history from the ticket itself.) |
| `GET /api/notifications` | The signed in user's notifications, newest first. The browser reloads them after every action and may poll. Alerts that depend on time (overdue, due soon) and the morning digest are the server's scheduled jobs |
| `POST /api/notifications/read` | Body `ids`. Marks them read. Laravel database notifications fit |

### 7.4 Master data, templates and forms
| Resource | Paths |
|---|---|
| Courier providers and branches | `GET /api/courier-providers`, `GET /api/courier-branches` |
| Asset Team users | `GET /api/asset-team` |
| HRIS team members | `GET /api/hris/team-members` |
| Checklist templates | `GET`, `POST`, `PATCH /api/checklist-templates/{id}`, `DELETE /api/checklist-templates/{id}`. A rejected write is a 422 whose first message the page shows |
| Email templates | `GET /api/email-templates`, `PUT /api/email-templates/{key}`, `DELETE /api/email-templates/{key}` |
| Retrieval forms | `GET /api/retrieval-forms`, `PUT /api/retrieval-forms/{id}`, `DELETE /api/retrieval-forms/{id}` |
| Form submissions | `POST /api/retrieval-forms/{slug}/submissions` |

The two editors save as you work. The browser sends one `PUT` for each form or template that
changed, a moment after the last edit, and one `DELETE` for each one removed. It never sends
the whole set. Both `PUT` bodies are the whole record:
- A form: its fields (`name`, `description`, `mode`, `status`, `theme_color`, `background`,
  `page_size`, `margins`, `category`, ...), `content` (the document HTML), `sections`
  (legacy), and `versions` (the saved versions).
- A template: `key`, `runtime` (`name`, `mode`, `description`, `subject`, `body`, `cc`, `bcc`,
  `status`, `attachment`, `attachment_form_id`, `background`, `footer_note`, ...), and
  `history` (the saved versions).

The `GET` answers the same records with `system: true` on those that ship with the product.
The id of a record created in the app is a UUID chosen by the browser, so a `PUT` creates it.
The developer may split `versions` / `history` into their own table and append to it
(section 4.5).

### 7.5 Public acknowledgment link (no login)
`GET /api/acknowledgments/{token}` returns only what the page prints, and
`POST /api/acknowledgments/{token}` records the signature. Rate limit both. The token is
`acknowledgment_token`. The link closes on the acknowledgment due date.

## 8. Response shapes

### 8.1 Single record (Eloquent API Resource)
```json
{
  "data": {
    "ticket_number": 426,
    "reference": "APR-26-00426",
    "status": "closed",
    "reason": "end-of-contract",
    "mode": "onsite",
    "lwd": "2026-10-01",
    "separation_date": "2026-10-05",
    "target_date": "2026-10-01",
    "assignee": { "id": 3, "name": "M. Bautista", "email": "m.bautista@goteam.io" },
    "employee": { "employee_id": "EMP-03310", "name": "Kevin Ong", "position": "Software Engineer" },
    "assets": [
      { "id": 11, "name": "Laptop", "model": "Lenovo ThinkPad X1 Carbon Gen 11",
        "type": "Computer Equipment", "serial": "SN-...", "asset_tag": "AT-...",
        "checked": true, "remarks": "", "resolution": "returned" }
    ],
    "checklist": [ { "id": 5, "position": 1, "text": "...", "required": true, "done": true } ],
    "files": [ { "id": 2, "kind": "proof_of_receipt", "original_name": "receipt.pdf",
                "mime": "application/pdf", "size": 48211, "download_url": "/api/files/2" } ],
    "created_at": "2026-10-13T01:20:00Z",
    "updated_at": "2026-10-13T08:50:00Z"
  }
}
```
Date-only fields are `YYYY-MM-DD` strings with no time or zone. Timestamps are ISO 8601
in UTC. The front end parses date-only values as **local midnight** (`parseLocalDate`),
because `new Date('2026-10-04')` is UTC midnight and shows the day before in timezones west
of UTC. Do not send a date-only value as a timestamp.

### 8.2 Lists
Laravel's standard paginator: `{ "data": [...], "links": {...}, "meta": { "current_page", "last_page", "per_page", "total" } }`.

### 8.3 Validation errors (HTTP 422)
```json
{ "message": "The given data was invalid.",
  "errors": { "authorizing_endorsement": ["The authorizing endorsement field is required."],
              "checklist.2.text": ["The text field is required."] } }
```
Keys use dot notation for nested paths. The front end maps this one shape onto its forms
(`setErrors`), so please keep Laravel's default validation response.

### 8.4 Business rule failures
Use HTTP 409 or 422 with a stable `code`, e.g. `{ "code": "ticket.duplicate_open", "message": "..." }`
for "this team member already has an open ticket". The front end shows `message` and may
branch on `code`.

### 8.5 Files
The prototype keeps uploaded files as browser object URLs (`blob:`), which cannot be saved.
Production:
- Upload with `multipart/form-data` to the action endpoint.
- Store with Laravel `Storage` (a private disk), save `path`, `original_name`, `mime`, `size`.
- Serve through an authenticated `GET /api/files/{id}` (no public URLs).
- The front end shape changes from `{ name, url }` to `{ id, original_name, mime, size, download_url }`.
- Limit types and size on the server (evidence: images and PDF).

## 9. Fixtures and the swap

Temporary data is isolated so the developer can delete it in one step. See
`BACKEND_SWAP.md` for what is on this seam today and the exact steps.

```
app/
  api/
    index.ts          the only module pages and stores use to reach the server. Picks mock or http (kept)
    keys.ts           snake_case to camelCase for responses, and back for request bodies (kept)
    mappers.ts        a ticket from the API to the shape the pages use (kept)
    types.ts          every call the api layer offers, and its action names (kept)
    http.ts           starter for the real backend, untested (developer corrects)
    mock.ts           the mock server: fixtures, the rules for checklist templates and creating
                      a ticket, and this browser's storage as the database (DELETE)
    ticketActions.ts  the rules the server owns for an open ticket, and the list of actions (DELETE)
  mocks/              fixtures, JSON (DELETE)
  data/recordSync.ts, syncedStores.ts   send changed forms and templates to the server (kept)
```

Rules for `mocks/*.json`:
- A fixture is exactly what the real endpoint would return inside `{ "data": [...] }`:
  snake_case keys, enum values and date formats as in this document.
- Identifiers the front end already uses as keys stay as they are. Courier providers and
  branches use their slug as `id` (`jrs-express`, `jrs-cebu-itpark`), and a branch points
  at its provider with `courier_id`. A Laravel Resource can expose `slug` as `id` and the
  provider's slug as `courier_id`. A seeder maps them back to its own bigint ids.
- Nested data that the endpoint returns nested stays nested (a team member's `shift` and
  `assets`).
- JSON, so a Laravel seeder can read the same files:
  `json_decode(file_get_contents(base_path('.../mocks/courier_providers.json')), true)`.

## 10. Default assumptions (to confirm after the demo)

These decisions belong to the developer, who has not yet seen the prototype. The front end
is built on the defaults below so work is not blocked. Each default is isolated so that
changing it later is cheap. Nothing here is a requirement until the developer confirms it.

| # | Decision | Default used now | Where a change lands |
|---|---|---|---|
| 1 | Who owns the stage rules (next stage, target date, gate requirements) | The server owns them. The prototype keeps its own copy only so the demo works, and treats it as a preview, not the authority | The stage engine in `app/constants/` stays or goes. Pages read results, not rules |
| 2 | R24 data: stored or live | **Revised.** Team member data comes from the AMS; R24 fields (last working day, separation date, shift, suggested reason) are fetched per ticket and not stored, except `lwd_seen` to detect changes | The `lwd_seen` column and one R24 mapper in `app/api/` |
| 3 | JSON naming | snake_case from Laravel, converted to camelCase at one boundary in `app/api/` | That one converter |
| 4 | Soft deletes | On email templates and retrieval forms. Tickets are never deleted | `deleted_at` columns |
| 5 | Ticket number and reference format | `ticket_number` auto-increment. `APR-YY-NNNNN` generated by the server | Server only. The front end only displays them |
| 6 | Rich text sanitising | Server sanitises `content` on save. The front end also escapes on render | Server only |
| 7 | Courier branch directory | A `courier_branches` table loaded by upload or manual entry | The table and one endpoint |
| 8 | Email sending and the morning digest | Out of scope for this module (copy and paste only), as in `DEV_HANDOFF.md` §10.4 | None in the front end |
| 9 | Realtime updates | Refresh on focus. The prototype's simulated reply detection is demo only | `app/prototype/` is deleted |
| 10 | Role permissions | Any signed in Asset Team member may act on any ticket. Takeover is recorded | Server policies. The front end hides nothing by role |

Everything above can be revisited in one short conversation after the demo. If an answer
differs from the default, only the file in the last column changes.
