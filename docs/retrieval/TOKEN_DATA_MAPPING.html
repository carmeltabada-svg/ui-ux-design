Token Data Mapping

Developer reference. For every {{TOKEN}} in the emails and forms: where the prototype gets the value, and whether production supplies it.

Every email template and form uses {{TOKEN}} placeholders. In the prototype they are filled from the ticket (function ticketTokenValues) or, for a preview with no ticket, from SAMPLE_VALUES. This file does not claim the production field names or types. We do not know them. It says instead whether the value is something production already holds, so the developer knows which tokens need a lookup and which the new module stores itself.

Yes

Comes from a production system. The value already exists in the AMS team member or asset records, or in R24 (HRIS). The developer maps it and fills in the real field and type in the last column.

No

Created by this module. The officer types it into the ticket, or the module works it out (a date rule, a count, a generated number). The new retrieval tables store it. Nothing to look up.

Open

No decision yet. The value is fixed text or a fixture in the prototype (couriers, company details, Asset Team members) and has no source system. The team decides where it lives: a settings table, master data or another system.

Resolution pipeline (prototype)

How tokens get resolved in the ticket workspace:
1. ticketTokenValues(ticket) maps the ticket to real values, one entry per token. An empty value stays undefined.
2. ticketResolvedCodeSet(ticket) keeps the tokens that have a real, non empty value.
3. placeholderStatusFor(code, resolved) returns resolved, org-constant, missing or unrecognized. Fixed company text is an org constant, so it is never flagged as missing.
4. wrapTokens(html, samples, statusFor) renders the colored preview.
5. expandTicketAssets(html, assets) repeats the asset table rows, one per confirmed asset.
6. expandCaseAssetRows(html, rows) repeats the charging table rows, one per case item.
7. resolveTokensForPrint(html, samples) produces the final email or form with every token filled.
Production should do the same on the server: resolve every token from the ticket, refuse to send while any is missing (the "Resolve placeholders before sending" rule), and print an unrecognized token as nothing.
