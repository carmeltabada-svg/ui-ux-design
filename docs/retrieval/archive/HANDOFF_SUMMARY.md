## Critical / non-obvious things a new session must know

1. **A `//` comment inside `<script setup>` that contains the literal substring `<template` (or presumably `<script`) breaks the build** with a cryptic Vite "Invalid end tag" 500 error whose reported line number is *past* the end of the file. Root-caused via extensive bisection this session: some part of this project's toolchain (never fully identified — not the Vue SFC compiler itself, which parses such a comment fine in isolation; suspected a regex-based block-boundary pre-scan from Nuxt/vite-plugin-vue-tracer/devtools) matches that substring even inside a plain-text comment and misreads it as a second template block. **Never write literal `<template>` or `<tr>`-style tag mentions in a `//` or `/* */` comment inside `<script setup>`** — describe them in prose instead ("this component's template has 5 sibling root rows"). This is now called out inline in `FormDocumentField.vue`'s own top comment. If a `.vue` file mysteriously 500s with a nonsensical line number after only comment/doc edits, this is the first thing to check.
2. **FormKit slot overrides replace the section's rendering *entirely*, including built-in behavior wired to that section, not just its visible content.** Concretely: overriding `#fileRemove` on a `<FormKit type="file">` to get custom-styled markup silently drops FormKit's own click-to-remove handler (`$handlers.resetFiles`, bound via an `onClick` schema attr on the section element itself, not something a child-content slot inherits). Found this via a real bug (remove button rendered fine but did nothing). Fix used throughout: when slotting a section that has built-in click behavior, wire the behavior back by hand against the same `v-model` ref (`removeFile(name)` filters `fileList.value` directly) — don't assume slotting a section keeps its default wiring.
3. **`v-bind="$attrs"` is mandatory on every root element of a multi-root component.** `FormDocumentField.vue`'s `<template>` has 5 sibling root `<tr>`s (one per field-type/layout branch). Vue only auto-forwards a parent's non-prop bindings (`@click`, `@dragstart`/`@dragover`/`@drop`/`@dragend`, `class`) onto a *single*-root component — on a multi-root one they're silently dropped. This was the root cause of two separate reported bugs this session (drag-and-drop not working, and clicking a field not opening its settings panel) — both fixed by adding `v-bind="$attrs"` to all 5 `<tr>`s.
4. **`definePageMeta({ ssr: false })` on a page does not stop the very first (direct/typed) request from being server-rendered** — it only stops SSR on subsequent client-side navigations to that route. `/form-preview.vue` needs `routeRules: { '/form-preview': { ssr: false } }` in `nuxt.config.ts` for that (already added) — this is what actually made a genuine SSR/localStorage hydration-mismatch bug (stale boxed/plain styling on first load of a real public link) go away. Don't remove that `routeRules` entry.
5. **Nuxt UI's `Checkbox` component defaults its `root` slot to `items-start`** (built for label+description pairs stacked top-aligned), which reads as "checkbox and label misaligned, label sitting too high" for a plain single-line checkbox+label. Fix per-instance: `:ui="{ root: 'items-center' }"`.
6. **A native `<input type="file">` always renders its own chosen-filename text natively, independent of and in addition to whatever FormKit's own file-item list renders** — this is what caused the "overlapping text" bug reported earlier. As of Round 4 this whole approach was replaced (see below) rather than patched further.
7. `nuxt typecheck` currently reports a fixed, small set of **pre-existing, unrelated** errors (email editor `Snapshot`/`HistoryEntry` type mismatches, a couple of `DropdownMenuItem` array-type complaints, one `UButton color` prop typed as bare `string`). None of this session's changes introduced new ones — every verification pass this session diffed against this same baseline list. If you see a *new* error not in that list, it's really new; if it's in that list, it was already there before this session started.
8. The dev server's in-memory `RETRIEVAL_FORMS`/`RETRIEVAL_FORM_SECTIONS` **resets to seed data on every dev-server restart** (expected — plain in-memory module state, not a bug). Whatever was true in localStorage from a previous test may not match what's live in a fresh reload until `hydrateFormsFromStorage()` runs (on `page:finish`). Don't chase a "regression" that's actually just this — reload once, or check `localStorage.getItem('ams:retrievalForms:v1')` directly, before concluding a section's boxed/plain state or a field's data is wrong.
9. Browser-automation quirk carried forward from the original handoff still applies: **screenshots in this tool occasionally render stale/blank/zoomed content** — cross-check via `get_page_text`, DOM `getBoundingClientRect()`/`getComputedStyle()`, or direct component-prop inspection (`el.__vueParentComponent`) rather than trusting one screenshot when something looks wrong.
10. When testing the builder's "Add field" flow via automation, **there are multiple "Add field" buttons on the page (one per section)** — `document.querySelectorAll('button')` matching on text alone will grab the *first* one in DOM order, not necessarily the one under the section you're trying to test. Reliable pattern used successfully throughout this session: find the section's own `<table>` by its content, then `table.nextElementSibling.querySelector('button')`.

## Round 4 fixes

- **File upload — full redesign** (this replaces the Round 3 chip approach entirely): a native `<input type="file">` always shows its own chosen-filename text *in addition to* whatever custom UI is layered on/around it — this was the real, unfixable-by-CSS-alone root cause of the original "overlapping text" bug. New approach in `FormDocumentField.vue`:
  - The FormKit file input is given an explicit `:id="fileInputId(field)"` and made fully invisible via `input-class="sr-only"` (still functional/focusable, just not rendered).
  - A real `UButton` (`as="label" :for="fileInputId(field)"`, `variant="outline"`) is the visible "Choose file" trigger — clicking a `<label for>` natively opens the file picker with zero extra JS.
  - **Boxed layout**: centered column (`flex flex-col items-center`). Empty state: button + "No file chosen" text side-by-side. Once a file's attached: button disappears, and the actual image renders (`URL.createObjectURL`, revoked/regenerated on every change) with a small ✕ overlay to remove it — a real preview for documentation purposes, not a filename chip.
  - **Plain layout**: same button/image logic, but the label + button + empty-state text stay inline on one line; the image, once attached, renders in its own block *below* that line (not inline with the label).
  - `openFile()` (click the image → opens in a new tab via a blob URL, browser's own viewer handles any download — never automatic) and `removeFile(name)` (filters `fileList.value` by name) are the two helper functions driving this; `removeFile` exists specifically because of gotcha #2.
- **Plain-layout padding inconsistency** — the plain branch's shared `<td>` hardcoded `px-3 py-3` regardless of layout, while static_text/signature/button_link's own plain style correctly used `py-1` with *no* horizontal padding. A field switched to plain therefore sat visually indented relative to its plain siblings. Fixed by dropping to `py-1` (no `px-3`) to match.
- **Submit-toggle sizing** — was 44px tall against every other overflow-menu item's 32px. Measured Nuxt UI's actual default item height (`p-1.5` ≈ 6px padding + text-sm line height ≈ 32px total) and matched it: `h-5` row height, `size="xs"` on the `USwitch`. Verified live at exactly 32px.
- **Background popover flashing open/closed in <1s** — the dropdown menu's own outside-click/focus-return sequence was still mid-flight when the popover's `open=true` was set synchronously in the same click handler, so the popover's own outside-click listener read that same interaction's tail end as "click outside" and closed itself almost immediately. Fixed by deferring the open with `nextTick()` in the `onSelect` handler.
- **Fade effect generalized** — added reusable `.fade-scroll-y`/`.fade-scroll-x` mask-image utilities to `app/assets/css/main.css` (a fixed mask, not scroll-position-tracked — correct for the short lists this app has). Applied to: the field-settings drawer's own scroll area, the History tab list (both forms and email editors), and every scrollable dropdown submenu (mode/status children pickers, "start from an existing template/form" pickers) in both `templates/index.vue` and both editor pages.
- **Field-settings drawer backdrop removed** — the mobile/narrow-viewport `<div class="fixed inset-0 bg-black/30" @click="emit('close')" />` behind the drawer was a full-viewport click/wheel/touch interceptor, which is exactly why the canvas behind it became unscrollable while the drawer was open. Removed entirely; the drawer's own ✕ close button is now the only way to dismiss it (clicking outside no longer closes it — an intentional trade-off given what was asked).

**A fourth issue took much longer to run down and is worth reading carefully**: after fixing the above three, inserting a field worked and even correctly wrote 8 fields into localStorage - but reloading the page always showed 7 again, as if the insert had never happened, despite the *storage* momentarily having the right value. Investigation went through several wrong turns before landing on the real cause, each instructive:

Not a real bug, but cost real debugging time before being ruled out; **closing stale tabs before trusting a "does this persist" test is worth doing early, not last**, next time this kind of cross-tab localStorage behavior is being debugged.
   - **End state, verified twice in a row**: insert a field → reload → field count matches → reload again → still matches. The fix that mattered was the live `computed` + explicit synchronous hydration; the `skipFirstUpdate` guard was a red herring that made things worse, not better.
